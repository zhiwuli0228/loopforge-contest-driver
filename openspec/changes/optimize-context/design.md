## Context

The C-to-Rust migration pipeline has 11 phases orchestrated by a main agent. The current delegation strategy in `work/skills/c-to-rust-migration-v2/SKILL.md` and `INSTRUCTION.md` marks Phase 3 (Spec) and Phase 4 (Plan) as "Keep inline", meaning the main agent writes all output files directly. An E2E session analysis (`session-ses_0ced.md`) confirmed this causes context explosion:

- Phase 3 wrote 14 spec files inline (each with detailed tables, scenarios, invariants)
- Phase 4 wrote `tasks.md` and `implement-plan.md` inline
- Phase 5 fabricated massive inline prompts (80+ lines of Rust signatures) instead of referencing `c2r-05-implement.md`
- By the time Phase 5 reached its third subagent, the context window was exhausted

Subagent prompt files (`c2r-03-spec.md`, `c2r-04-plan.md`, `c2r-05-implement.md`) already exist and are well-structured. The fix is to enforce their use through the orchestration rules.

## Goals / Non-Goals

**Goals:**
- Eliminate context explosion by delegating all phases that produce multiple output files (>3) to subagents
- Enforce subagent prompt file references (by path) rather than inline-constructed prompts
- Implement dynamic batch scheduling for Phase 5 that adapts to any batch count and dependency structure
- Keep main agent context under control regardless of migration size (5 capabilities or 50)

**Non-Goals:**
- Rewriting subagent prompt files (c2r-*.md) — they are already adequate
- Changing the overall 11-phase pipeline structure
- Adding new tools or dependencies
- Modifying the tools.py data layer

## Decisions

### Decision 1: Phase 3 and Phase 4 changed to Delegate

**Rationale**: Both phases produce N output files where N scales with project size. Phase 3 writes one spec per capability (minimum 1, observed 14). Phase 4 writes 2 files but the content size scales with batch count. Running these in subagents isolates the output content from the main context. The subagent prompt files `c2r-03-spec.md` and `c2r-04-plan.md` already exist with complete instructions.

**Alternatives considered**:
- Keeping inline but compressing outputs: still puts content in main context, just less of it. Doesn't scale.
- Splitting Phase 3 into per-capability subagents: over-engineered; one subagent writing all specs in a loop is simpler and the subagent has its own full context window.

### Decision 2: Phase 5 dynamic scheduling algorithm

The main agent parses `implement-plan.md` to discover batches at runtime:

```
1. Parse implement-plan.md → extract {batch_id, priority, dependencies} for all batches
2. Group by priority: P0, P1, P2
3. For current_priority in [P0, P1, P2]:
   a. Find batches at current_priority with all deps satisfied
   b. Dispatch them in parallel (one subagent per batch, referencing c2r-05-implement.md)
   c. Wait for all to return gate tokens
   d. Mark completed batches as done, advance to next priority
```

**Rationale**: Batch count and dependency structure are generated by Phase 4 and vary per project. Hardcoding batch dispatch logic (e.g., "always dispatch KV and TSL in parallel") would break when Phase 4 generates different batch groupings.

**Alternatives considered**:
- One subagent for all batches: fails for the same reason keeping Phase 3 inline fails — context explosion inside the subagent.
- SKILL.md hardcodes batch dependencies: brittle; any change to Phase 4 output format breaks it.

### Decision 3: Subagent prompt file path reference

Instead of:
```
Agent(prompt="You are implementing Batch 1-6...\n\n80 lines of Rust signatures...")
```

The main agent uses:
```
Agent(prompt="Execute work/subagent/c2r-05-implement.md with BATCH_ID=5.1, SOURCE_ROOT=..., OUTPUT_DIR=..., OPENSPEC_CHANGE=...")
```

**Rationale**: The prompt file reference is ~2 lines. The fabricated prompt is 80+ lines. With 13 batches, the difference is ~1,000 lines of context saved. The subagent itself reads the prompt file from disk in its own context.

### Decision 4: Gate token compression

Subagents return `PHASE_PASS` + one-line summary (e.g., "6 modules, 29 tests pass"). Full implementation reports stay in the subagent's context and are discarded.

**Rationale**: The main agent only needs to know pass/fail/degraded to decide whether to proceed to the next phase. Detailed results are available in the generated files on disk if needed.

## Risks / Trade-offs

- [Risk] Subagent isolation means main agent loses visibility into intermediate file contents → Mitigation: If a phase fails (PHASE_BLOCKED), the main agent reads the phase's output directory to diagnose, but only on failure.
- [Risk] Parallel Phase 5 batch dispatch could cause Cargo.toml conflicts if two batches both create project files → Mitigation: The first P0 batch (or an explicit "Batch 0") is responsible for project skeleton; other batches only modify their own module files.
- [Risk] Dependency parsing from implement-plan.md could fail if Phase 4 changes its output format → Mitigation: The parsing is straightforward (regex for "依赖 batch:" lines); if parsing fails, fall back to sequential execution as a safe default.
- [Trade-off] More subagent invocations (up to 13 for Phase 5 alone) means more API calls → Acceptable because context explosion prevention is higher priority, and parallel dispatch amortizes wall-clock time.
