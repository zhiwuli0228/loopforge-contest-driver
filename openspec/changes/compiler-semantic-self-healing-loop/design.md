## Context

Change 3 生成 Rust 工程，Change 4 迁移测试并执行差分验证；两者产生的编译、测试和语义差异是本变更唯一允许使用的修复依据。竞赛规则要求提交包对目标工程零定制，因此仓库内不能包含 FlashDB 名称、领域概念、符号前缀、目录布局、API/错误码表、预期行为或专用补丁模板。另一方面，单个诊断无法修复时不能使无人值守流程异常终止：系统必须保存异常、继续独立阶段，在全部编码验证结束后再统一复修一次，最终仍未解决则明确报告。

该设计把“执行成功”和“合规成功”分开：runner 必须正常完成并发布证据；只有全部合规门禁通过时才可给出通过结论。降级继续保证流程可用，但绝不把未解决异常转换成合规成功。

## Goals / Non-Goals

**Goals:**

- 从结构化编译、测试和差分诊断生成可追溯、最小化的 Rust 修复。
- 对无法修复的问题实施非失败式降级、末尾统一复修和完整异常报告。
- 证明修复未删除/弱化测试、绕过门禁、扩大修改范围或无说明地增加 `unsafe`。
- 用至少三次固定类别故障注入验证检测、修复及回归闭环。
- 以静态和运行时双重检查保证实现不包含任何目标项目定制。

**Non-Goals:**

- 不修改只读 C 源工程、预加载设计输入或差分 Oracle。
- 不预先编码任何目标项目业务语义，也不依据名称猜测修复意图。
- 不保证任意缺陷都能自动修复；无法证明的修复必须保留为未解决异常。
- 不负责正式 Linux 干净环境 E2E，后者属于 Change 6。

## Decisions

### 1. 采用运行证据驱动的领域中立 Repair IR

所有诊断先归一化为 Repair IR，至少包含运行身份、来源阶段、工具、诊断类别、位置、相关实现/测试 ID、可观察期望、允许修改根和证据摘要。修复器只读取 Repair IR 与当次生成工程，不读取项目 profile 或根据名称分派。

选择该方案是为了使修复输入可审计并可做定制扫描。直接将原始日志交给自由式修复器虽然简单，但难以限制证据边界和补丁范围。

### 2. 使用阶段队列和显式异常台账，禁止异常冒泡终止编排

每个修复单元产生 `repaired`、`deferred` 或 `unresolved` 结果。解析失败、补丁冲突、命令启动失败、超时或验证失败均转换成结构化异常项，保留原始错误并进入 deferred 队列；runner 继续执行不依赖该修复的阶段。顶层还必须捕获阶段异常并发布最小有效报告。

这里的“不失败”指流程不得崩溃或丢失报告，不代表门禁自动通过。存在 unresolved 项时，最终合规结论必须明确为未满足，而进程与报告发布仍正常完成。

### 3. 两段式修复调度

第一段在每个编码/验证阶段后执行有界局部修复循环：归一化诊断、生成单一意图补丁、应用到临时工作树、运行目标验证，通过后再运行完整回归。达到轮次上限或证据不足时进入 deferred 队列。

第二段在所有编码与验证流程结束后执行一次统一复修。它可以利用后续阶段新增的诊断，但仍受相同证据边界和补丁限制。复修失败后不再循环，转为 unresolved 并写入最终报告，避免无限自愈。

### 4. 补丁在隔离副本验证后原子提交

候选补丁先应用到生成 Rust 工程的隔离副本。依次检查路径白名单、变更行相关性、测试/断言完整性、`unsafe` 差异、目标测试和完整回归；全部通过才原子提交到生成工程。失败候选被丢弃但证据保留。

相较直接修改主输出，该方案避免半成品污染后续阶段，也便于准确生成前后差异。

### 5. 补丁相关性由图和诊断位置决定，不由项目名称决定

允许修改集合为诊断文件、关联实现节点及调用/类型依赖图上的直接依赖；测试文件默认只读。只有诊断明确证明生成测试本身存在机械性编译错误时才可修改测试，同时必须证明源断言映射、断言强度和数量不变。超出允许集合的候选补丁直接拒绝并记入台账。

### 6. 防 FlashDB 定制采用提交包静态扫描与运行时路径溯源

静态扫描修复代码、规则、模板和 fixture，拒绝目标项目名称（大小写及常见变体）、已知领域词、符号/目录特判和固定业务计数。运行时记录每个修复决策所引用的 Repair IR 字段和证据路径，验证不存在内置 profile、默认项目身份或名称分支。测试 fixture 使用领域中立的最小 Rust/C 样例，不能复制目标项目 API 或布局。

仅做关键词扫描不足以发现间接定制，因此还需检查配置来源、分支条件和决策溯源；反之，扫描命中运行产物中的目标文本不应误判，检查范围限定为提交包的实现、规则与静态测试资产。

### 7. 固定故障矩阵以抽象缺陷类别表示

故障注入覆盖类型不匹配、借用冲突、未解析符号、可观察返回差异、状态转换差异和边界 off-by-one。每类至少三个独立重复运行，种子和基线哈希固定并记录。注入器按 Rust AST/IR 节点类别选择位置，不按目标 API 名称选择。

每轮输出独立目录，包含注入补丁、原始诊断、repair task、候选修复、变更范围、目标验证和完整回归日志；汇总报告不得用部分成功掩盖失败重复。

### 8. 报告使用不可真空的聚合状态

最终报告记录尝试总数、成功、deferred、复修成功、unresolved、被完整执行的故障类别/重复次数以及证据路径。计数必须与逐项记录一致，缺失日志、零故障实例或陈旧运行身份都形成异常。报告发布器采用临时文件加原子替换，并提供兜底最小报告，确保异常路径也有输出。

## Risks / Trade-offs

- [流程继续可能导致级联诊断噪声] → 用依赖标记区分根异常与被阻塞阶段，只对拥有独立有效前置条件的阶段继续执行，并在报告中关联级联项。
- [最小修改边界可能拒绝必要的跨模块修复] → 允许基于调用/类型依赖图的一跳扩展；仍不足时记录 unresolved，不静默扩大范围。
- [自动修复可能生成语义正确但难以证明的补丁] → 只有目标验证、差分验证和完整回归全部通过才提交，否则降级记录。
- [定制扫描出现误报或漏报] → 将静态词法扫描、配置/AST 分支审计和运行决策溯源组合，并限定扫描资产边界。
- [故障注入三次带来运行成本] → 对目标验证并行化但保持完整回归隔离；缓存只复用内容哈希和运行身份完全一致的不可变构建输入。
- [正常退出可能被误解为验收通过] → 独立发布 `execution_status` 与 `compliance_status`，禁止由进程退出码推导合规结论。

## Migration Plan

1. 定义 Repair IR、异常台账和证据 schema，并为旧日志提供只读适配器。
2. 引入隔离补丁执行器、范围审计和两段式调度，但先以观察模式生成报告。
3. 接入目标验证、完整回归、测试完整性和 `unsafe` 门禁。
4. 增加领域中立故障注入矩阵及三次重复验证。
5. 启用静态定制扫描和运行决策溯源，删除任何遗留项目 profile/专用规则。
6. 将 runner 切换为异常台账驱动的非失败式完成与原子报告发布。

回滚时可关闭补丁提交、保留观察与报告模式；不得恢复目标项目专用修复或让异常跳过报告。
