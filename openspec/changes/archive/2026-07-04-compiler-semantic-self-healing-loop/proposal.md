## Why

编译、测试和差分验证能够暴露生成 Rust 工程中的缺陷，但当前流程缺少项目无关、可审计且不会因单个修复失败而中断的自愈闭环。比赛提交又严格禁止任何 FlashDB 定制，因此必须仅依据当次运行产生的诊断与证据生成最小修复，并把无法修复的问题降级记录、末尾复修和明确报告，而不是让编排流程失败。

## What Changes

- 建立由 Rust 编译器、目标测试、完整回归和 C/Rust 差分结果驱动的通用诊断、修复、验证闭环，修复范围仅限生成的 Rust 工程。
- 对错误类型、借用冲突、未解析符号、返回值差异、状态转换错误和边界错误执行项目无关的最小补丁生成，不内置或识别 FlashDB 名称、符号、目录、API、错误码、行为规则或专用修复模板。
- 每个阶段遇到无法修复的异常时记录结构化诊断并降级继续后续可执行流程；任何单项修复失败均不得导致编排器异常退出或遗漏最终报告。
- 在全部编码与验证阶段结束后，对尚未解决的异常统一执行一次最终复修；复修仍失败时保留原始证据、尝试历史和影响范围，并在报告中明确标记未解决异常。
- 对固定故障类型执行至少三次注入、检测与修复验证，并产生原始缺陷、诊断、修复补丁、变更范围、目标验证和完整回归证据。
- 强制防伪门禁：不得删除测试、减少测试数量、弱化断言、绕过差分验证、扩大无关补丁范围或引入未说明的 `unsafe`；门禁异常同样进入降级与最终复修/报告流程。

## Capabilities

### New Capabilities

- `diagnostic-repair-orchestration`: 基于当次运行诊断执行项目无关的最小修复、多轮验证、异常降级和末尾统一复修。
- `repair-integrity-verification`: 通过故障注入、补丁范围审计、测试与断言完整性检查及回归证据证明修复未绕过门禁。

### Modified Capabilities

无。

## Impact

- 影响测试迁移与差分验证之后的 runner 编排，以及 `work/runtime/` 中的诊断归一化、修复计划、补丁应用、回归执行、异常台账和报告发布逻辑。
- 消费 Change 3/4 产生的生成 Rust 工程、实现映射、测试映射、差分向量及日志；不得修改只读 C 源项目或提交包内的通用规则。
- 新增逐轮 `injected-defect.patch`、`compiler-or-test-error.log`、`repair-task.json`、`generated-repair.patch`、`changed-lines.json`、`targeted-test.log`、`full-regression.log`，以及汇总修复与未解决异常报告。
- 后续 Linux E2E 验收必须消费本变更的完整证据链；存在未解决异常时不得伪报完全合规，但流水线仍须正常结束并发布明确报告。
