## Why

现有五个核心变更分别覆盖真实源码分析、语义规划、Rust 工程生成、差分验证和自愈，但尚缺少在干净 Linux 环境中从只读输入、空输出目录开始运行整个提交包的最终证明。比赛会直接淘汰包含 FlashDB 定制的方案，因此最终验收还必须独立证明提交路径只由通用证据驱动，并在工具或修复异常时完整结束、复修和报告，而不能崩溃、漏报或伪报合格。

## What Changes

- 新增正式 Linux 无人值守 E2E 编排，从空的输出、结果和日志目录执行完整迁移与验证，并连续运行两次验证可重复性。
- 支持 `SOURCE_ROOT` 直接指向目标 C 工程或其上层目录、输入工程没有 README 等正式场景；项目定位只能依据通用 C 工程结构和可审计证据。
- 将源码树作为只读输入，记录运行前后的文件集合、内容、权限和符号链接证据，并验证完全不变。
- 新增提交包零定制审计，覆盖实现、规则、提示词、模板、fixture、配置、默认值、文件名和控制流；禁止任何 FlashDB 名称、领域概念、符号、API、路径、布局、黄金结果或专用修复。
- 建立非失败式阶段编排：不可修复异常写入台账并降级继续所有独立可执行阶段；全部编码与验证结束后统一复修一次，仍失败则明确写入最终报告。
- 分离 `execution_status` 与 `compliance_status`：流程和报告发布必须完成，但任何残留异常、缺失证据、定制命中或硬门禁失败均不得输出 `READY_FOR_EVALUATION`。
- 原子发布环境、构建、测试、unsafe、源码完整性、定制审计、异常台账和最终验证证据，并确保 `result/output.md` 与 `result/issues/00-summary.md` 状态一致。

## Capabilities

### New Capabilities

- `clean-linux-e2e-orchestration`: 在干净 Linux 环境中从只读输入和空输出开始，无人值守、可重复地执行完整提交流程。
- `zero-target-customization-audit`: 对提交资产与运行决策执行静态和动态审计，证明不存在任何目标项目定制或特判。
- `resilient-final-acceptance-reporting`: 以异常台账、末尾复修和原子报告实现非失败式执行，同时严格区分流程完成与合规通过。

### Modified Capabilities

无。

## Impact

影响 Linux 入口脚本、项目根定位器、主 runner、阶段调度、最终验证器、报告发布器、提交资产扫描器及其集成测试。最终验收将消费前五个核心变更的同一次运行证据，不允许复用仓库内预生成 Rust 文件、陈旧日志或跨运行缓存；`SOURCE_ROOT` 和提交规则保持只读。
