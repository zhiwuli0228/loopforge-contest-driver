## Context

前五个核心变更已定义从源码分析到编译与语义自愈的证据链，但仓库当前仍可能受预生成输出、陈旧日志、宿主机状态或目标项目特判影响。Change 6 必须在正式 Linux 环境中验证提交包本身：只读 `SOURCE_ROOT`，清空输出与报告目录，按两种输入布局连续执行两次，并只用同次运行证据作出结论。

比赛的淘汰规则要求提交实现对 FlashDB 零定制。目标名称、领域词、符号或路径作为外部输入和日志数据出现是不可避免的，但它们不能存在于提交包静态资产中，也不能影响分支、配置、定位、生成、修复、比较或验收决策。与此同时，任何阶段异常均不能导致顶层流程失败或缺失报告：异常必须进入台账，独立阶段继续，全部编码验证结束后统一复修一次。正常完成执行不等于合规通过。

## Goals / Non-Goals

**Goals:**

- 在受控 Linux 环境中，从空可写目录和只读真实输入运行完整流水线并生成自包含证据。
- 用通用结构发现而非项目身份支持直接根目录、上层目录和无 README 场景。
- 静态审计提交资产、动态审计决策来源，发现任何直接或间接目标定制即判定不合规。
- 对异常实施有界降级、依赖隔离、末尾一次复修和不可丢失的明确报告。
- 验证源码完整性、Cargo 构建与测试、unsafe 比例、前五个变更证据、两次运行一致性和报告一致性。

**Non-Goals:**

- 不在本变更中重新实现前五个变更的分析、生成、测试或修复算法。
- 不通过项目名称、已知目录、API、固定数量、黄金输出或专用配置提高目标工程通过率。
- 不承诺存在残留异常时仍满足比赛合规；只保证执行与报告发布不因异常中断。
- 不把工程验证宣称为数学形式化等价证明。

## Decisions

### 1. 使用一次性 Linux 沙箱和只读输入挂载

每次验收创建新的运行 ID 和隔离根目录，将提交包以待测形态装入、将 `SOURCE_ROOT` 只读挂载，并为 output、logs、result、临时目录和 Cargo target 分配空目录。网络默认关闭或记录允许的依赖来源；工具链版本、内核、架构、locale、时区和环境变量写入 `linux-environment.json`。

选择一次性环境而非清理当前工作树，可消除未跟踪文件、缓存和权限残留。验收不得读取仓库内现有 `work/output`、`logs/trace`、`result` 或其他运行的缓存；需要依赖缓存时只能使用内容寻址、只读且不包含生成源码或验收结论的工具链缓存。

### 2. 项目根通过通用候选与可解释评分解析

解析器只根据通用 C 工程证据建立候选，例如源/头文件、构建描述、include 关系和测试目录；不得使用项目名称、领域词、符号前缀、特定文件名组合或 README 内容作为特判。直接根与上层目录走同一算法。唯一最高分候选才可继续；零候选或并列歧义写入异常台账，不猜测默认根。

相较为正式目标配置路径提示，这一方案符合比赛的泛化约束，并能通过领域中立 fixture 独立测试。

### 3. 用阶段 DAG 承载非失败式编排

每个阶段声明输入证据、输出证据、可写根、依赖和超时。阶段结果为 `completed`、`degraded`、`skipped_dependency` 或 `exception`；异常被规范化进 append-only 台账，顶层不得因子阶段异常退出。只有前置证据有效的独立阶段才继续，以避免级联错误被误认为根异常。

操作系统无法启动进程、磁盘写满等基础设施问题也必须尽力发布最小兜底报告；若连兜底目标都不可写，入口在 stderr 输出同一结构化摘要。这里的“不得失败”指 runner 完整收敛并报告，而不是强制所有验证通过。

### 4. 全部编码验证后恰好进行一次统一复修

局部修复无法解决的项目进入 deferred 队列。编码、构建、测试、差分和完整性检查全部完成或降级收敛后，调度器使用同一运行新增证据对每项 deferred 异常再尝试一次，不扩大可写边界、不放宽门禁。复修成功必须重跑受影响验证；复修失败转为 unresolved，保留两次尝试和原始证据。

恰好一次末尾复修可利用后续证据，同时避免无限循环。不可修复项不再抛出异常，而是确定性进入最终报告。

### 5. 零定制采用静态清单扫描、结构审计和动态污点溯源

静态审计范围由提交 manifest 明确列出，覆盖代码、脚本、规则、技能、提示词、配置、模板、fixture、测试和文件/目录名。扫描目标名称及变体、领域知识、符号/API、错误码、布局、固定业务计数、黄金输出和专用补丁；进一步解析配置和控制流，发现间接 profile、默认身份、哈希映射或编码后的分派。

动态审计为根定位、阶段选择、生成、测试、修复和最终判定记录决策溯源，允许来源仅为通用配置 schema 与当次输入分析证据。外部输入或日志中的目标字符串标记为 tainted data，若进入控制条件或策略选择即直接不合规。只做关键词扫描会同时漏掉间接定制和误报输入证据，因此必须组合三类证据。

### 6. 最终判定使用双状态与不可真空门禁

`execution_status` 描述编排是否收敛并发布报告，预期即使有业务异常也为 `COMPLETED_WITH_EXCEPTIONS`；`compliance_status` 仅在所有硬门禁通过、异常台账无 unresolved、定制审计无命中时为 `READY_FOR_EVALUATION`。退出码只表示入口是否完成协议，不能被用于推导合规状态。

最终验证器必须检查非零源码/API/测试/差分/实际测试计数、映射完整、unsupported 为零、Cargo 命令成功、unsafe 严格小于 10%、输入不变、两种布局成功、连续两次一致且所有证据属于当前运行。任一缺失或不一致都明确列为异常并禁止就绪状态。

### 7. 两次运行以语义归一化清单比较

每个场景连续运行两次，每次使用新空目录。比较生成文件相对路径、内容哈希、结构化报告和门禁结论；仅对显式声明的运行 ID、时间戳、绝对临时路径和无语义随机值做规范化。规范化规则固定、项目无关并写入证据，不能忽略源代码、测试、计数、诊断或状态差异。

### 8. 证据分层暂存并原子发布

阶段证据先写入运行专属暂存区，带 schema 版本、run ID、输入摘要和内容哈希；最终验证完成后原子发布。至少包括环境、源码前后快照、构建/测试日志、unsafe 报告、定制审计、异常台账、可重复性报告、`final-verification.json` 和两份人读报告。报告器失败时使用独立最小发布器，且摘要中的计数、状态和路径必须由机器报告派生。

## Risks / Trade-offs

- [降级继续产生级联噪声] → 通过阶段 DAG、前置有效性和 `skipped_dependency` 区分根异常与依赖影响。
- [目标字符串扫描误报运行输入] → 静态提交资产与动态输入证据分区，输入数据允许出现但禁止影响控制流。
- [编码、别名或间接配置逃避关键词扫描] → 加入结构化配置审计、控制流审计、文件名审计和动态决策溯源。
- [正常退出被误认为验收通过] → 双状态、机器可读硬门禁和报告中的醒目残留异常列表共同约束。
- [两次运行受时间戳等无语义值影响] → 使用最小白名单规范化，并审计每个被忽略字段。
- [只读挂载不足以证明输入不变] → 同时记录文件集合、内容、权限和符号链接的前后快照并比较。
- [兜底报告也因环境故障无法落盘] → 使用预先打开的报告目录句柄并同步写 stderr；将基础设施异常明确记录，绝不输出就绪。

## Migration Plan

1. 定义 Linux 运行 manifest、阶段结果、异常台账、定制审计和最终验证 schema。
2. 将 Linux 入口切换到一次性目录与阶段 DAG，先以观察模式保留旧入口作对照。
3. 接入通用根定位、只读输入校验和同次运行证据聚合。
4. 接入末尾一次复修、原子报告和最小兜底报告。
5. 加入静态/结构/动态零定制审计及领域中立的正反测试 fixture。
6. 执行两种 `SOURCE_ROOT` 布局、无 README、异常降级和连续双跑验收，随后移除旧的非隔离路径。

回滚只能回到不提交合规结论的观察模式；不得恢复目标专用配置、复用陈旧产物或跳过异常报告。

## Open Questions

无。正式实现不得新增目标项目 profile；新增环境差异只能通过项目无关、版本化且在报告中展开的运行配置表达。
